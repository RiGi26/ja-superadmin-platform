## Precise classification

An E1 decision must concern a **new creation intent**, not a request to claim an existing workspace. Identity is the verified Core issuer and durable subject plus authoritative customer/entity linkage, not email equality. The broker must establish all of the following from sources it is authorized to query completely:

1. An immutable Core-issued creation intent identifies this exact subject, new workspace intent, exact action, canonical name/key hashes and authoritative onboarding/provisioning source revision. No existing tenant/workspace/portal is being adopted. A random UUID or a row ID supplied by the requester does not establish this.
2. Complete history coverage for the customer/entity and its verified aliases: no prior Company/membership, revoked/retired ownership, tenant/portal association, legacy claim/import/mapping, financial history or disputed/pending ownership. Sources must include retained history, not just active rows visible through customer RLS. Account recreation or a new email cannot erase existing history. Any missing linkage or history-retention coverage means UNKNOWN.
3. Existing/pending onboarding or provisioning for the same entity is reconciled with the exact new intent. The allowed current new-intent record is not itself legacy evidence; all other intents, invitations, retries, provisions and imported records must be accounted for. A count of zero in an empty DEV database is not coverage of actual Core history.
4. A versioned decision contains source IDs/revisions, completeness and retention guarantees, captured-at/fresh-until bounds, decision reason, issuer/subject/session, action, scope and payload digest. It is issued by the authorized broker, never populated from request booleans or reviewer counts.
5. Relevant legacy/provisioning/dispute/financial writers participate in a serialization or revision-fence contract. A subject advisory lock in a new registry does not serialize existing writers. After waiting, compare current source revisions and revalidate managed identity. Any uncovered writer or changed/incomplete revision denies.
6. The Company, creator Owner membership, receipt and audit event commit atomically, with a durable actor/key uniqueness boundary. Exactly matching retry may return the same result only under current session/Owner authorization. Changed payload, changed source decision or lost authority denies.

Classification is E1 only when every condition is trusted, complete, current and proven at runtime. Existing/history-positive paths classify E2/E3 and cannot use bootstrap even with two operators; they need the independent S1 adjudication command. Contradictory, unavailable, stale, RLS-hidden, incompletely mapped or untrusted evidence classifies UNKNOWN. E2/E3 operator decisions must bind two distinct subjects and sessions to the same immutable case/action/scope/source revisions, revalidate their current authorization after waits, exclude requester/self-approval, and audit both approvals. No such command is implemented here.

`screenFirstOwnerClaim` is private denial-only screening. Untrusted history-positive/legacy/disputed claims can force E2/E3 hold. Zero claimed history still returns UNKNOWN, `canBootstrap:false`. It cannot certify history or grant E1 status. SQL `assert_first_owner_authority` independently refuses unconditionally.

## One concrete W1 transport proposal

Proposed design: **protected server-issued assertion records**, consumed through a dedicated executor connection by a private atomic writer. No browser RPC, bearer JWT forwarding, GUC authority, service-role bypass or request-supplied actor is used as the database authority. The following is a decision-ready contract, not a new installed table or credential.

1. Core server-only policy boundary receives an ordinary cookie-bound request. It verifies the exact DEV Core issuer/audience/subject, current managed session and account eligibility through the approved verification mechanism. It validates the strict E1 v2 string adapter and derives the permitted action and complete classification from trusted sources. Internal allowlists/custom roles can deny, never grant customer ownership.
2. A separately scoped **verifier connection principal**, accessible only to that server boundary, can issue protected assertion records in a private assertion store through a fixed private issuer function. It has no Company/audit mutation authority. It cannot be a generic `service_role` client. Its exact login, issuer-function owner, managed Auth/source read privileges and connection facility are UNAPPROVED and not provisioned.
3. Assertion fields bind: opaque cryptographically random assertion ID; issuer and subject; managed session ID; intended executor audience and exact project ref; exact action `new_company_initial_owner`; creation-intent/source ID and revision; eligibility classification and decision/version/coverage digest; canonical lowercase UUID key, scope SHA-256, payload SHA-256 and codec `e1:v2`; issued-at, expires-at and random nonce; issuing principal and consumption receipt. No tokens, email, credentials or raw evidence are persisted in the assertion/audit. Database access control on the trusted issuer is the authenticity mechanism; fields/UUID secrecy alone are not proof.
4. Proposed freshness for Owner decision: database `clock_timestamp()` defines a maximum 30-second unconsumed assertion lifetime, with issuance/revalidation at the trusted boundary and no client-provided time. Reject future-issued, expired or mismatched records. This bound is a proposal, not an approved security parameter or a claim about Auth expiry.
5. A different **executor login** connects server-to-DB over verified TLS using a reviewed non-Production direct/session connection. Its only application authority is a membership in the existing NOLOGIN `wz_core_executor`, explicitly ADMIN FALSE, INHERIT TRUE, SET FALSE. The login itself is NOSUPERUSER/NOBYPASSRLS/NOCREATEROLE/NOCREATEDB/NOREPLICATION, cannot CREATE or acquire any owner/verifier role, and has no table/Auth DML/read privileges. Exact login and secure secret handling remain unapproved. Membership INHERIT TRUE is explicit PG17 permission, not inferred from role attributes. No executor reaches the browser bundle, callback or public Data API.
6. Proposed future private signature is `bootstrap_company(assertion_id uuid, name text, key uuid)`. This is **not** the current two-argument source function. The writer verifies its approved executor session principal, locks the assertion row and subject, compares database-generated scope/fingerprint with the protected assertion, revalidates current managed identity, source revisions and classification after all waits, and refuses before insertion if any binding changed. Atomic assertion consumption joins Company/Owner/event/receipt commit. Audit records the decision/source/assertion correlation and action. A future assertion store requires its own isolated owner, grants, constraints and recovery revision; it is not silently included in the current four-role scaffold.
7. Used assertion IDs/nonces are not reusable for new writes. An exact request retry obtains a **new current verified assertion** and may read the durable receipt only after current authorization; changed payload/source/action/actor/session cannot reuse an old approval. Unconsumed expiry does not invalidate a previously committed receipt; a receipt never serves as a live authorization token.
8. Membership reads and later Owner commands need their own approved action-scoped assertions and transaction revalidation against canonical Company membership, including active Company/status/role and exact selector comparison. The current proposal has no positive customer read policy; matching a unit fixture does not enable the Hub.

Trust boundaries are browser → Core policy; Core policy → verifier credential; protected assertion store → restricted executor; private definer → non-bypass RLS tables. The verifier is an explicit trusted policy component; compromise of it is a material authority compromise, not solved by random UUIDs. Executor compromise must not permit creating/altering assertions or changing their binding. Separate credentials, role closure, issuer API restrictions, protected store integrity and Auth/source verification must all be demonstrated before the transport guard can change.

Connectivity assumes an approved zero-cost application host can reach this DEV database with a dedicated principal, strict TLS validation and stable one-backend transactions. No direct/session pooler/IPv4 availability, secret store, hosting or role login capability is inferred from project Free status. Transaction pooling is unacceptable unless tested to preserve the exact transaction, principal and revalidation semantics. No provider configuration or infrastructure change is authorized now.

Revocation acceptance concerns a defined validation checkpoint: revocation effective **before the writer's final post-wait/pre-mutation verification** must deny even with an unexpired access JWT. Supabase documents that JWT validity can outlive sign-out, so current session checks are required; `getClaims()` alone is insufficient. Verify provider propagation/refresh/account-disable behavior and a safe narrow session-validity helper. If a revocation races after that checkpoint, it cannot undo a committed operation; do not claim instantaneous serializability with managed Auth without a provider-supported locking/ordering protocol. The same constraint applies to legacy/source writers. Any missing protocol remains a blocker. See [Supabase sessions](https://supabase.com/docs/guides/auth/sessions).

## Consolidated implementation update, 15 October 2026

Selected source design is ROLLBACK_ONLY_ROLE_REHEARSAL. PG17's bootstrap-superuser-granted creator ADMIN cannot be revoked by a non-superuser creator. Explicit installer SET grants and automatic ADMIN are distinct grantor records; neither a guaranteed loss of all recovery authority nor zero final membership is established. No retained permanent grant is selected. Current SQL ends in ROLLBACK and every guard stays unconditional. Durable installer/recovery is blocked on actual provider evidence; [PG17 role attributes](https://www.postgresql.org/docs/17/role-attributes.html) supplies the corrected engine contract, not managed execution proof.

The private local W1 envelope schema now tests the bindings above, required complete coverage before/after waits and denial for stale/revoked/changed/missing fields. Complete mock E1 envelopes still block on transport. These are structure/consistency checks, not trusted classification or live operator proof. No assertion store, issuer credentials, executor login, or session access is provisioned. Source revision/fence equality alone cannot prove that other writers actually honor those fences.
